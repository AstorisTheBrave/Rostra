## what this is

How Rostra's pieces fit together: how it scales across shards, how a slash command flows from a user to
a database and back, and how the optional services (Redis, top.gg, Lavalink) plug in. The full design
lives in `docs/superpowers/specs/2026-06-05-unified-bot-core-platform-design.md`.

## technical map

**Phase 00 extraction status (2026-10-17):** runtime entrypoints and modules remain under `src/`.
Shared owners are `@rostra/config`, `@rostra/logger`, `@rostra/database`, `@rostra/cache`,
`@rostra/i18n`, `@rostra/discord-ui`, `@rostra/contracts` and `@rostra/testing`. Their explicit export
maps resolve ESM TypeScript source, matching the existing `tsx` runtime and no-emit build. No compiled
package artifacts are needed at runtime. Package typechecks use the shared strict configuration and
do not inherit the root alias.

Config is the only runtime environment reader; database owns the single Prisma constructor and
exports generated model types. Logger depends on config; cache and database depend on both. The cache
`/bus` export owns Redis pub/sub, and i18n `/live` consumes cache/database/logger without depending on
gateway internals. The i18n root remains the pure translator; `/bundled`, `/commandLocalizations`,
`/locales` and `/validate` expose optional entrypoints. Discord UI exports all components at its root
and acknowledgement through `/safeAck`. The dependency graph is acyclic and checked at the root gate.

The shared `JobDefinition` lives in contracts. Gateway-specific `BotModule` and `BotClient` types
remain in `src/types/module.ts` for Task 4; its job type re-export is the sole temporary type seam.
Tenant preferences, scheduler, cron, gateway services and asset-bound card rendering stay with the
runtime until their owning slices. All migrated callers already use package imports.

Prisma schema and historical migrations live in `packages/database/prisma/`. Root `prisma.config.ts`
retains migration URL and dotenv behavior; the separate generation config stays credential-free.
The database package declares the existing Prisma CLI so its client resolves beside the schema.
The Docker install layer includes every package manifest before frozen installation. History has
byte-level SHA-256 tests and disables checkout line-ending conversion. Service migration, image and
rollback execution remain unverified here and belong to the deployment slice.

**existing process topology (runtime still in the root application)**
```
cluster.ts (manager)
  ├─ ShardingManager (auto shards, respawn)
  ├─ Fastify: /health, /health/shards, /metrics, /votes/topgg
  ├─ top.gg autoposter (aggregates guild count across shards via IPC, then posts)
  └─ N × bot.ts (one BotClient per shard)
        ├─ loaders: commands, events, interactions, jobs (auto-discover src/modules/*)
        ├─ services: getPrisma(), getCache(), getLogger(), createIpc(client)
        └─ BullMQ workers (in-process; splittable later)
```

**sharding / IPC** - `src/cluster/ipc.ts` defines an `Ipc` interface (`broadcast`, `fetchValues`).
Today it's `NativeIpc` (discord.js `broadcastEval`). Switching to `discord-hybrid-sharding` later is a
`SHARDING_MODE=hybrid` config change + a `HybridIpc` class - modules never touch the sharding lib.

**command flow (target)**
1. User runs `/mod ban …` → `interactionCreate` on a shard.
2. Pipeline: resolve command → permission guard → cooldown (Redis bucket) → Zod-validate options →
   `execute(ctx)` inside an error boundary.
3. Handler uses `getPrisma()` for data, `getCache()`/`getRedis()` for hot data, and replies via
   `packages/discord-ui/src/components.ts` (Components V2).
4. Errors → ephemeral V2 error message + structured Pino log with a trace id.

**command namespacing** - ~16–18 top-level commands (`/mod`, `/economy`, `/ticket`, …) each holding
subcommand groups/subcommands, to stay under Discord's 100-global-command cap. Map is in the spec §8.

**data** - one Postgres schema (`packages/database/prisma/schema.prisma`) merges all 15 bots' storage. Redis holds
leaderboards (sorted sets), hot config cache, rate limits, and job queues.

**depends on**
- `packages/config/src/index.ts` - every subsystem reads typed config from here
- `@rostra/database`, `@rostra/cache`, `@rostra/logger` - shared singleton owners

## gotchas

- top.gg stats must be posted from the **manager** process (aggregate across shards), not per shard -
  per-shard counts are partial.
- Build order matters: foundation → runtime → feature modules (see `docs/sessions/log.mdx` and the spec).
