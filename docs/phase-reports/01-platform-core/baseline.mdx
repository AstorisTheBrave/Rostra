# Phase 01 platform baseline

## Preserved registry

The Phase 00 checked fixture records 42 module IDs, 47 normalized command definitions and 48 Discord
event registrations. The focused parity tests load the registry without a Discord login or command
publication. This is a structural baseline, not a performance measurement.

## Measurement host

The Task 1 harness was developed on Windows 10.0.26300, AMD Ryzen 5 5500H, 15.4 GiB RAM, eight logical
processors, Node.js 24.19.0. These host details are not representative deployment capacity. Runtime and
iteration count are required on every workload so later measurements can be compared only when metadata
matches.

## Workload paths

| Workload | Existing path and evidence | Iterations | Measurements |
| --- | --- | ---: | --- |
| Registry parity | `tooling/scripts/snapshot-commands.mjs`, `snapshot-modules.mjs` and checked fixtures | One parity run in the Phase 00 gate | 42 modules, 47 commands, 48 events; prior run took 8.4 s on its recorded host |
| API authorization | `GET /internal/v1/guilds/:guildId/summary`, exact-guild authorization and denial tests in `apps/api/src/server.test.ts` | No latency samples captured | Pending service-backed sample capture |
| Tenant cache read | L1, Redis L2 and database fallback in `apps/gateway/src/services/tenant.ts` | No cache-path samples captured | Pending disposable PostgreSQL/Redis sample capture |
| Durable operation | API acceptance, PostgreSQL claim fencing and worker duplicate/restart proof | CI owns service and process-restart workload | Functional proof exists; latency and queue-lag samples not captured |

Phase 00 evidence reports command durations and service outcomes but did not capture API p95, query counts,
event-loop delay, cold/warm tenant-cache timings or queue lag. The Task 1 harness defines the validated
input and deterministic comparison format for those samples; it does not synthesize missing values.
This baseline therefore remains PENDING until runner-backed samples are attached. No production
throughput, latency, capacity or memory claim is made.

## Comparison contract

Each JSON workload has a stable identity, runtime string, positive iteration count and one finite,
non-negative sample per iteration for request latency, database query count, event-loop delay, cold and
warm cache latency, and queue lag. The comparison tool rejects missing samples or mismatched workload,
runtime or iteration metadata. It reports request, event-loop and queue p95 values, mean query count and
mean cold/warm cache latency in stable key order.

Service, browser and process-kill workloads remain on GitHub runners. Do not run process interruption or
disposable-service workloads as part of the lightweight local gate.
